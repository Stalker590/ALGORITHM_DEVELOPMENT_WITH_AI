# AI-Driven Engineering Starter Kit: От идеи до продакшена без архитектурного хаоса

Этот набор шаблонов превращает разработку с помощью терминальных ИИ-агентов (OpenCode, Claude Code, Antigravity CLI и др.) из хаотичной генерации кода в строгий, воспроизводимый инженерный конвейер с разделением ролей **«Аналитик → Архитектор → Строитель»**.

---

## Состав стартового комплекта

| Файл | Назначение | Кто использует |
| :--- | :--- | :--- |
| **`README.md`** | Пошаговое руководство по запуску нового проекта с нуля (этот файл) | Разработчик |
| **`HOW_TO_CREATE_CONTEXT.md`** | Методика 4-раундового брейншторма и эталон структуры `CONTEXT_OF_PROJECT.MD` на ~500 строк | Разработчик + ИИ-Аналитик |
| **`ARCHITECT_PROMPT.md`** | Системный промпт для Главного архитектора, который разворачивает всю инженерную документацию проекта | ИИ-Архитектор |

---

## Полный цикл создания проекта с нуля (5 этапов)

```text
[Этап 0: Инициализация]
       │
       ▼
[Этап 1: Brainstorm -> CONTEXT_OF_PROJECT.MD (~500 строк)]  <-- HOW_TO_CREATE_CONTEXT.md
       │
       ▼
[Этап 2: Проектирование -> PLAN_OF_PLAN, TECH_CONTEXT, INVARIANTS, ROADMAP, AGENTS, AI_RULES_WORK]  <-- ARCHITECT_PROMPT.md
       │
       ▼
[Этап 3: Атомарная разработка -> Этап 1.1 -> Тест -> Commit -> /new -> Этап 1.2...]
       │
       ▼
[Этап 4: Отладка по протоколу Root Cause First (при необходимости)]
```

---

### Этап 0. Подготовка чистого репозитория

Создай пустую папку проекта, инициализируй Git и скопируй туда стартовые файлы (либо держи их в своей базе знаний Obsidian):

```bash
mkdir my-project && cd my-project
git init
```

Убедись, что у тебя настроены базовые инструменты окружения (компилятор/рантайм, СУБД, `.env` для секретов и `.gitignore`, чтобы в репозиторий не попали пароли, логи и временные бинарники).

---

### Этап 1. Создание «ДНК проекта» — `CONTEXT_OF_PROJECT.MD`

Никогда не начинай писать код со слов *«Сделай мне сервис/сервер/приложение»*. Сначала создай в корне проекта файл **`CONTEXT_OF_PROJECT.MD`** объёмом **450–600 строк** плотной технической и продуктовой конкретики.

1. Открой **`HOW_TO_CREATE_CONTEXT.md`**.
2. Проведи с ИИ **4 раунда брейншторма** по инструкции из Части 1:
   * **Раунд 1 (Brain Dump):** Опиши суть идеи, стек, нагрузку и попроси ИИ задать 15 самых неудобных вопросов по бизнес-логике, безопасности и крайним случаям.
   * **Раунд 2 (Стресс-тест):** Ответь на вопросы своими словами, зафиксируй жизненный цикл сущностей, формулы расчётов и поведение при сбоях.
   * **Раунд 3 (Scope & Constraints):** Жёстко отсеки лишние фичи из версии 1.0 (MVP) и запиши запреты (типы данных, кодировки, лимиты).
   * **Раунд 4 (Сборка монолита):** Попроси ИИ скомпилировать всё в единый файл `CONTEXT_OF_PROJECT.MD` строго по **10 разделам из Части 2** файла `HOW_TO_CREATE_CONTEXT.md`.
3. **Обязательно вычитай `CONTEXT_OF_PROJECT.MD` глазами** и прогони по **Чек-листу из Части 3** (убери «и так далее», впиши точные числа, лимиты и связи между модулями).
4. Зафиксируй фундамент в Git:
   ```bash
   git add CONTEXT_OF_PROJECT.MD
   git commit -m "docs(init): создан CONTEXT_OF_PROJECT.MD"
   ```

---

### Этап 2. Проектирование архитектуры (Режим «Архитектор»)

Теперь превращаем продуктовое описание в строгую инженерную спецификацию и дорожную карту.

1. Открой терминальный ИИ-агент в корне проекта, начни чистую сессию (`/new`) и включи режим глубоких размышлений (`thinking: high` / `max`).
2. Открой **`ARCHITECT_PROMPT.md`**, скопируй его содержимое целиком и отправь агенту.
3. Агент выполнит полный аудит `CONTEXT_OF_PROJECT.MD` и последовательно создаст **6 инженерных документов** в корне репозитория:
   * **`PLAN_OF_PLAN.MD`** — мастер-план связи документов и сквозной реестр сущностей.
   * **`TECH_CONTEXT.MD`** — стек, структура папок, схема БД, потоки данных, контракты API/UI и команды сборки.
   * **`INVARIANTS.MD`** — нумерованный реестр неприкосновенных правил (`INV-01`..`INV-XX`), нарушение которых запрещено.
   * **`ROADMAP.MD`** — декомпозиция всего проекта на Фазы и **атомарные Этапы (`1.1`, `1.2`, `1.3`...)** по 2–5 файлов на каждый.
   * **`AGENTS.MD`** — системная инструкция и чек-лист самопроверки (`Diff Audit`) для агентов-строителей.
   * **`AI_RULES_WORK.MD`** — регламент взаимодействия разработчика и ИИ.
4. Проверь сгенерированные файлы глазами (особенно `TECH_CONTEXT.MD`, `INVARIANTS.MD` и первый блок `ROADMAP.MD`) — убедись, что агент уже сделал первый архитектурный коммит.

---

### Этап 3. Атомарная разработка (Режим «Строитель»)

Дальше ты работаешь по строгому конвейеру. **Главное правило: 1 атомарный Этап из `ROADMAP.MD` = 1 чистая сессия `/new`.** Не отдавай агенту целую Фазу разом.

#### Стандартный цикл одного этапа:

1. **Старт сессии:** Введи `/new` в агенте (старый мусор переписки очистится, а базовые документы подтянутся из серверного кэша почти бесплатно).
2. **Постановка задачи:** Отправь короткий промпт:
   > «Изучи CONTEXT_OF_PROJECT.MD, TECH_CONTEXT.MD, INVARIANTS.MD, AGENTS.MD и ROADMAP.MD. Выполни строго Этап [X.Y] из ROADMAP.MD по регламенту AGENTS.MD: реализуй код в рамках Scope этапа, закрой все указанные Edge Cases, прогони сборку/тесты, выполни Diff Audit по INVARIANTS.MD, обнови статус в ROADMAP.MD и сделай коммит.»
3. **Ручная проверка разработчиком (3–5 минут):**
   * Запусти проект локально и проверь базовый пользовательский сценарий из `Definition of Done` этого этапа.
   * **Никогда не начинай этап `X.2`, не проверив вживую этап `X.1`.**
4. **Переход дальше:** Если всё работает — снова `/new` и берёшь следующий этап.

---

### Этап 4. Протокол исправления багов и регрессий (`Root Cause First`)

Если после выполнения очередного этапа всплыл баг или сломалась старая механика:

1. **Не делай `/new`**, если ошибка обнаружена сразу после выполнения текущего этапа и касается только что изменённых файлов (пока контекст прогрет). Если баг всплыл позже или в другом модуле — начни с `/new`.
2. **Не пиши абстрактное «не работает, почини»**. Используй шаблон:
   > «После выполнения Этапа [X.Y] возникла регрессия:
   > 1. Симптом и условия воспроизведения: [что именно ломается и при каких действиях, а когда работает нормально].
   > 2. Зона поиска: [какие файлы менялись в последнем коммите].
   > 3. Выполни задачу строго по шагам: сначала найди точную строку причины (Root Cause Analysis) и объясни её; затем внеси исправление с соблюдением INVARIANTS.MD; прогони сборку/тесты и `git diff` по затронутым файлам; сделай коммит `fix(...): ...`.»

## 5 золотых правил выживания при работе с ИИ

1. **Документация — единственный источник истины:** Если ты решил поменять архитектуру или добавить новую механику в середине проекта — сначала обнови `TECH_CONTEXT.MD` и `ROADMAP.MD`, и только потом проси агента писать код.
2. **Атомарность экономит деньги и нервы:** Маленький этап на 2–4 файла выполняется быстрее, дешевле и с нулём регрессий в старом коде.
3. **Чистый Git перед каждым шагом:** Никогда не запускай агента на новую задачу при грязном `git status`. Если агент запутался и испортил код — не уговаривай его 20 сообщений подряд, а сделай `git reset --hard HEAD`, уточни задачу и запусти заново в `/new`.
4. **Смоук-тест и Diff Audit обязательны:** Компиляция без ошибок не гарантирует отсутствие логических багов в рантайме. Всегда держи в проекте скрипт быстрого автозапуска/проверки и заставляй агента проверять `git diff` до коммита.
5. **Разделяй думание и рутину:** Сложное проектирование и поиск багов делай на максимальном уровне рассуждений (`thinking: high`), а типовые этапы по готовой спецификации — на стандартном/быстром режиме.
